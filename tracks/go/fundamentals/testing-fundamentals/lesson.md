# Testing Fundamentals — Go

## Why Go's Testing Story Is Different

Coming from JavaScript/TypeScript, your mental model of testing is probably built around Jest or Vitest: a test runner you install separately, an `expect` assertion library with a rich API, `describe`/`it` blocks for organization, `beforeEach`/`afterEach` hooks, mocking libraries, and a separate binary you invoke.

Go ships with all of that in the standard library. No separate test runner. No assertion library to choose. `go test` is part of the toolchain. This isn't minimalism for its own sake — it's an intentional design decision. The Go team observed that testing frameworks tend to grow into mini-languages of their own, and that most of what they provide can be done with plain functions and table-driven data.

When you write Go tests, you're writing Go. Not a test DSL layered on top of Go.

---

## How `go test` Works Under the Hood

When you run `go test ./...`, the Go toolchain:

1. Finds every file ending in `_test.go` in the package
2. Compiles the package together with its test files into a temporary test binary
3. Runs that binary, collecting output
4. Reports pass/fail per test function

The test binary is a regular Go program. Its `main()` is generated by the toolchain and calls each `Test*` function in sequence. This means your tests run in the same process as the code under test — no network boundaries, no serialization overhead.

Test files are part of the package they test. A file called `ratelimit_test.go` in package `ratelimit` can access unexported identifiers. This is sometimes called **white-box testing** and it's idiomatic in Go for unit tests. If you want to test only the public API (black-box), you use `package ratelimit_test` (note the `_test` suffix on the package name) — the test file is compiled separately and can only access exported identifiers.

```go
// White-box test — same package, can access unexported fields
package ratelimit

func TestInternal(t *testing.T) {
    l := &limiter{tokens: 5}  // unexported field, accessible
    // ...
}
```

```go
// Black-box test — external test package, only exported API
package ratelimit_test

import "yourmodule/ratelimit"

func TestPublicAPI(t *testing.T) {
    l := ratelimit.New(5, time.Minute)  // only public surface
    // ...
}
```

Most Go projects mix both approaches.

## The Anatomy of a Test Function

```go
func TestAdd(t *testing.T) {
    result := Add(2, 3)
    if result != 5 {
        t.Errorf("Add(2, 3) = %d, want 5", result)
    }
}
```

Rules:
- The function name must start with `Test` (capital T) followed by a non-lowercase letter
- The only parameter is `*testing.T`
- No return value
- A test fails if `t.Error`, `t.Errorf`, `t.Fatal`, or `t.Fatalf` is called before the function returns

### `t.Error` vs `t.Fatal`

This distinction matters more than it appears:

```go
func TestValidation(t *testing.T) {
    result, err := Parse("")
    if err == nil {
        t.Error("expected error for empty input, got nil")
        // execution continues — we fall through to the next check
    }

    if result != nil {
        t.Fatal("expected nil result on error")
        // t.Fatal stops this test immediately — the line below won't run
    }

    // this runs even if the t.Error above fired
    fmt.Println("reached this line")
}
```

Use `t.Error`/`t.Errorf` when the test can continue meaningfully — subsequent checks are independent. Use `t.Fatal`/`t.Fatalf` when continuing would cause a panic or give misleading results (e.g., you got a nil pointer when you expected a value, and the next line dereferences it).

### Compared to JS/TS (Jest)

```typescript
// Jest
test('Add', () => {
    expect(Add(2, 3)).toBe(5);
    // throws AssertionError if fails — execution stops at first failure
});
```

```go
// Go
func TestAdd(t *testing.T) {
    result := Add(2, 3)
    if result != 5 {
        t.Errorf("Add(2, 3) = %d, want 5", result)
        // execution continues by default
    }
}
```

The key difference: Jest's `expect` throws on failure, stopping the test. Go's `t.Error` marks the test as failed but continues. This means a single Go test function can report multiple failures in one run, which is often more useful for debugging.

## Table-Driven Tests — The Go Idiom

In Jest you might write one `it` block per case. In Go, the idiomatic approach is to define a slice of test cases and loop over them. This is called **table-driven testing**.

```go
func TestParseAmount(t *testing.T) {
    tests := []struct {
        name    string
        input   string
        want    int
        wantErr bool
    }{
        {name: "valid integer", input: "42", want: 42},
        {name: "valid negative", input: "-10", want: -10},
        {name: "empty string", input: "", wantErr: true},
        {name: "non-numeric", input: "abc", wantErr: true},
        {name: "overflow", input: "99999999999999999999", wantErr: true},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseAmount(tt.input)
            if (err != nil) != tt.wantErr {
                t.Errorf("ParseAmount(%q) error = %v, wantErr %v", tt.input, err, tt.wantErr)
                return
            }
            if err == nil && got != tt.want {
                t.Errorf("ParseAmount(%q) = %d, want %d", tt.input, got, tt.want)
            }
        })
    }
}
```

Why this works well:
- Adding a new test case is one line in the slice — no new function, no new `it` block
- All cases are visible in one place — the table is self-documenting
- The pattern is consistent across the codebase — anyone reading a Go project knows where to look
- `t.Run` gives each case its own name and isolates its failures

The naming convention `tt` for the test case variable is a Go convention you'll see everywhere. `tt.name` for the subtest name is also standard.

### The `name` field matters

When a subtest fails, Go prints:
```
--- FAIL: TestParseAmount/non-numeric (0.00s)
```

Without names you get `TestParseAmount/#00`, `TestParseAmount/#01` — useless for debugging. Always name your table test cases.

## Subtests with `t.Run`

`t.Run(name, func)` creates a **subtest**. Each subtest:
- Has its own `*testing.T`
- Can be run in isolation: `go test -run TestParseAmount/valid_integer`
- Can be run in parallel (see below)
- Appears as a nested result in verbose output

```go
t.Run("valid integer", func(t *testing.T) {
    // ...
})
```

The name goes through URL encoding — spaces become underscores. So `-run TestParseAmount/valid_integer` matches `"valid integer"`.

### Parallel Subtests

Calling `t.Parallel()` inside a subtest signals that it can run concurrently with other parallel tests:

```go
for _, tt := range tests {
    tt := tt  // capture the loop variable — critical before Go 1.22!
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel()  // this subtest can run concurrently
        // ... test body ...
    })
}
```

> **Warning:** The `tt := tt` capture is essential before Go 1.22. Without it, all subtests share the same `tt` variable (the loop variable), and by the time they run (after the loop), `tt` holds the last value. This is the same loop closure gotcha from functions-and-closures.
>
> As of Go 1.22, loop variables have per-iteration scope, so `tt := tt` is no longer needed — but you'll see it in existing codebases.

## Test Helpers with `t.Helper()`

When you extract repeated test logic into a helper function, call `t.Helper()` at the top. This tells the testing framework that the helper is not the test itself — errors should be reported at the **call site**, not inside the helper.

```go
// Without t.Helper() — errors point to the wrong line
func assertEqual(t *testing.T, got, want int) {
    if got != want {
        t.Errorf("got %d, want %d", got, want)
        // failure reported here — inside assertEqual — not useful
    }
}

// With t.Helper() — errors point to the caller
func assertEqual(t *testing.T, got, want int) {
    t.Helper()
    if got != want {
        t.Errorf("got %d, want %d", got, want)
        // failure now reports the line where assertEqual was called
    }
}
```

```go
func TestSomething(t *testing.T) {
    result := compute(5)
    assertEqual(t, result, 42)  // failure reported HERE when t.Helper() is used
}
```

Without `t.Helper()`, the failure points to line 3 of `assertEqual`. With it, it points to the `assertEqual(t, result, 42)` call in your test. This is the difference between "something inside a helper failed" and "this assertion in this test failed."

## Benchmarks

Benchmark functions follow the same convention as tests, but use `*testing.B` and must start with `Benchmark`:

```go
func BenchmarkTokenBucket(b *testing.B) {
    limiter := NewTokenBucket(1000, time.Second)

    b.ResetTimer()  // don't count setup time

    for i := 0; i < b.N; i++ {
        limiter.Allow()
    }
}
```

`b.N` is determined automatically by the benchmark runner. It starts small and increases until the benchmark produces stable results. You don't set `b.N` — you use it.

Run benchmarks with:
```
go test -bench=. -benchmem
```

The `-benchmem` flag adds allocation counts — how many heap allocations per operation and how many bytes. These numbers are often more useful than raw timing for identifying optimization opportunities.

### `b.ResetTimer()`

Setup code before the loop shouldn't count toward the benchmark:

```go
func BenchmarkParseConfig(b *testing.B) {
    // Setup: load a large config file
    data, err := os.ReadFile("testdata/large-config.json")
    if err != nil {
        b.Fatal(err)
    }

    b.ResetTimer()  // start timing here — don't count file I/O

    for i := 0; i < b.N; i++ {
        _, _ = ParseConfig(data)
    }
}
```

Without `b.ResetTimer()`, the file read time is included in the benchmark — your benchmark is measuring I/O, not parsing.

### `b.ReportAllocs()`

Forces allocation reporting even without `-benchmem`:

```go
func BenchmarkStringBuilder(b *testing.B) {
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        buildMessage("user-123", "payment failed", 42)
    }
}
```

Useful when you're explicitly optimizing for allocations (zero-alloc hot paths).

### `b.StopTimer()` and `b.StartTimer()`

For more granular control — pause the timer during cleanup:

```go
func BenchmarkWithCleanup(b *testing.B) {
    for i := 0; i < b.N; i++ {
        obj := NewExpensiveObject()
        b.StartTimer()

        // Only time the operation itself
        obj.DoWork()

        b.StopTimer()
        obj.Cleanup()  // don't time cleanup
    }
}
```

### Compared to Rust

```rust
// Rust — requires criterion crate (external benchmark harness)
use criterion::{criterion_group, criterion_main, Criterion};

fn benchmark_parse(c: &mut Criterion) {
    c.bench_function("parse", |b| b.iter(|| parse_input("test")));
}

criterion_group!(benches, benchmark_parse);
criterion_main!(benches);
```

Go's benchmarks are built into the standard toolchain. Rust's built-in benchmarks (`#[bench]`) are nightly-only, so most Rust projects use the `criterion` crate instead. Go avoids external dependencies for the testing workflow.

## Fuzzing

Go 1.18 introduced native fuzzing. A fuzz test looks like this:

```go
func FuzzParseAmount(f *testing.F) {
    // Seed corpus — known interesting inputs
    f.Add("0")
    f.Add("42")
    f.Add("-1")
    f.Add("9223372036854775807")  // math.MaxInt64

    f.Fuzz(func(t *testing.T, input string) {
        // This function is called with both corpus and generated inputs.
        // It should not panic — that's a fuzz failure.
        result, err := ParseAmount(input)
        if err == nil && result > math.MaxInt32 {
            t.Errorf("result %d exceeds expected maximum", result)
        }
    })
}
```

Run as a normal test (executes only the seed corpus):
```
go test -run FuzzParseAmount
```

Run in fuzzing mode (generates inputs automatically):
```
go test -fuzz=FuzzParseAmount -fuzztime=30s
```

When fuzzing finds a failure, it saves the input to `testdata/fuzz/<FuzzTestName>/`. On subsequent `go test` runs, that saved input is always re-tested — it becomes part of your regression suite automatically.

### The `testdata/` Convention

`testdata/` is a directory convention the Go toolchain respects:
- `go test` includes `testdata/` in the test binary's working directory
- `testdata/` is ignored by the Go build system (it won't be compiled)
- Fuzz failures are saved to `testdata/fuzz/<TestName>/`
- You can store fixture files, golden files, and sample inputs here

```
package/
├── parser.go
├── parser_test.go
└── testdata/
    ├── valid-config.json
    ├── invalid-config.json
    └── fuzz/
        └── FuzzParseAmount/
            └── abc123          # saved fuzz failure input
```

## Test Doubles: Fakes, Stubs, and Mocks

Go's approach to test doubles is interface-based and framework-free. If you design your code to depend on interfaces rather than concrete types, tests can inject lightweight implementations.

### The Vocabulary

- **Stub**: Returns hardcoded responses. Has no logic.
- **Fake**: Has real logic, but uses in-memory storage or simplified behavior instead of production dependencies (e.g., an in-memory database instead of PostgreSQL).
- **Mock**: Verifies that specific methods were called with specific arguments. Often generated by frameworks; in Go, often hand-written.
- **Spy**: Like a stub, but records calls for later inspection.

The Go community leans heavily on **fakes** and **stubs** — they're straightforward to write and maintain. Mocks that verify exact call sequences tend to be brittle (they break when implementation details change).

### The Pattern: Depend on Interfaces

```go
// Production code depends on this interface
type Clock interface {
    Now() time.Time
}

// Production implementation
type RealClock struct{}

func (RealClock) Now() time.Time {
    return time.Now()
}

// The type under test takes a Clock, not time.Now directly
type RateLimiter struct {
    clock    Clock
    maxRate  int
    // ...
}
```

```go
// Test implementation — a stub
type StubClock struct {
    t time.Time
}

func (s *StubClock) Now() time.Time {
    return s.t
}

func (s *StubClock) Advance(d time.Duration) {
    s.t = s.t.Add(d)
}
```

```go
// Test uses the stub
func TestRateLimiter_ResetsAfterWindow(t *testing.T) {
    clock := &StubClock{t: time.Unix(0, 0)}
    limiter := NewRateLimiter(5, time.Minute, clock)

    for i := 0; i < 5; i++ {
        if !limiter.Allow() {
            t.Fatalf("request %d unexpectedly denied", i+1)
        }
    }

    if limiter.Allow() {
        t.Error("6th request should be denied")
    }

    clock.Advance(time.Minute)  // advance time — no sleep needed

    if !limiter.Allow() {
        t.Error("first request after window reset should be allowed")
    }
}
```

Without the `Clock` interface, you'd be at the mercy of wall clock time. The test would need a `time.Sleep(time.Minute)` — slow, flaky, and painful. With the interface, you control time.

### Compared to JS/TS (Jest mocks)

```typescript
// Jest — mock the entire module
jest.mock('../clock');
const mockNow = jest.fn().mockReturnValue(new Date('2024-01-01'));
(Clock.now as jest.Mock) = mockNow;

// Or use jest.spyOn
jest.spyOn(Date, 'now').mockReturnValue(1704067200000);
```

```go
// Go — inject the dependency via interface
clock := &StubClock{t: time.Unix(0, 0)}
limiter := NewRateLimiter(5, time.Minute, clock)
```

Go's approach is more explicit — you must design for testability upfront by accepting interfaces. Jest can mock modules after the fact through module system interception. The Go approach is more code but leads to better-designed systems: code that's easy to test is usually better designed (no hidden global state).

## `TestMain` for Setup and Teardown

Sometimes you need global setup before any tests run — starting a test database, loading fixture data, initializing a logger. `TestMain` handles this:

```go
func TestMain(m *testing.M) {
    // Setup: runs before any test in this package
    db := setupTestDatabase()
    testDB = db  // assign to package-level variable

    code := m.Run()  // run all tests

    // Teardown: runs after all tests
    db.Close()

    os.Exit(code)
}
```

Rules:
- `TestMain` replaces the normal test runner — you must call `m.Run()` yourself
- You must call `os.Exit(m.Run())` (not just `m.Run()`) — `os.Exit` skips deferred functions, but `TestMain` doesn't return to the runtime in the normal way, so `os.Exit` is required to propagate the exit code
- Only one `TestMain` per package is allowed
- It's a heavy-handed tool — prefer table tests and setup helpers when possible. `TestMain` is for things that truly need to be shared across all tests in a package.

## `go test` Flags Reference

```bash
# Run all tests
go test ./...

# Verbose output (print each test name and result)
go test -v ./...

# Run only tests matching a pattern (regex)
go test -run TestRateLimit ./...
go test -run TestRateLimit/window_reset ./...  # match subtest

# Run each test N times (useful for flaky test detection)
go test -count=3 ./...

# Race detector (catches data races in concurrent code)
go test -race ./...

# Coverage
go test -cover ./...
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out  # open in browser

# Run benchmarks (tests are skipped by default)
go test -bench=. ./...
go test -bench=BenchmarkTokenBucket ./...
go test -bench=. -benchmem ./...      # include allocation stats
go test -bench=. -benchtime=5s ./...  # run each benchmark for 5s

# Fuzz
go test -fuzz=FuzzParseAmount -fuzztime=30s ./...

# Short mode — tests can check t.Short() and skip expensive work
go test -short ./...

# Timeout (default is 10 minutes)
go test -timeout=60s ./...

# No caching (go test caches results — -count=1 disables)
go test -count=1 ./...
```

### Compared to Jest/Vitest

```bash
# Jest
npx jest --verbose
npx jest --testNamePattern="RateLimit"
npx jest --coverage

# Go equivalent
go test -v ./...
go test -run TestRateLimit ./...
go test -cover ./...
```

The conceptual mapping is close. Go's `-run` takes a regex; Jest's `--testNamePattern` also takes a regex. Go uses `-count=1` to disable caching (Jest doesn't cache test results between runs).

## Putting It Together: The Testing Mindset in Go

Go testing has a few opinions baked in that are worth internalizing:

1. **Test behavior, not implementation.** Your tests should break when behavior changes, not when you rename a private variable.

2. **Make tests deterministic.** Use stub clocks, in-memory stores, and injected dependencies to eliminate flakiness.

3. **Table tests for combinatorial inputs.** If you find yourself copying a test and changing one value, that's a table test waiting to happen.

4. **Helpers should call `t.Helper()`** so failures point to the right place.

5. **Benchmarks measure what you think they measure.** `b.ResetTimer()` before the loop. `-benchmem` always.

6. **The testing package is enough.** Resist the urge to pull in `testify`. The idiomatic Go style — explicit `if` checks, descriptive error messages — is more readable to newcomers and doesn't add a dependency.
